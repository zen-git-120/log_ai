# log_ai

## 1. サービス概要

log_aiは、複数のAIにまたがる日々の活用記録を一箇所に集め、GitHub風の草カレンダーで継続を可視化するサービスです。AIという技術が好きな人が、誰かと比べるためではなく自分のために、目標設定や下準備なしに記録するだけで継続の証を積み上げられます。

- **誰の、どんな課題を、どう解決するか**: 仕事・家事・育児に追われ学習時間が短く、AIに要約させて眺める/コピペするだけで記録が終わっている人の、「インプットだけで理解が定着しない」「複数のAIにまたがる活用が振り返りにくい」という課題を、目標設定や予定管理などの下準備を必要としない、シンプルな記録+草カレンダーの仕組みで解決する。

## 2. このアイデアはどこから生まれたか

**2-1. きっかけとなった体験・感情**

複数のAI(3種類)を使っていて、1日AIを使って何をしたかを復習するために、それぞれのAIに聞いたり要約してもらったりする手間があるのが嫌だった。また、AIを使った学習とAIを使わない学習を分けて記録したいという思いもあり、AIを使った学習記録があればいいと考えた。さらに、記録をつけた日をGitHubの草のように可視化できたら、学習に対するモチベーションも上がると感じた。

**2-2. なぜそれが「気になった」のか**

AIという技術そのものが好きで、AIの使い方やスキルは人によって異なるという面白さがあり、工夫すること自体が楽しい。新しいスキルを作ったり、YouTubeやネット記事で見つけた面白そうなスキルを自分のPCで実装してみたりしている。「今日AIを使ってこんなスキルを実行してみた」という活用術を記録できれば、自分のAIの使い方が見えるし、AI学習の振り返りにもなると考えた。

## 3. 課題の整理

**3-1. 表に見えている困りごと**

3種類のAIを使っていて、それぞれチャット欄も手順もプロンプトも異なるため、個別に聞く必要があり手間がかかる。また、AIに今日の活動内容の要約を出してもらってそれを眺めるだけでは学習効果が薄く、アウトプットとして思い出しながら記録をつける場所が欲しいと感じた。

**3-2. 本当に解決したい課題は何か(「なぜ?」を3回)**

1. なぜ複数のAIにまたがる活用の振り返りが面倒だと困るのか → AIに要約させて眺めるだけではインプット止まりになり、明日にはほぼ忘れている可能性が高い。記録をつけながら思い出すことで、インプットだけで終わらずアウトプットの機会になる。記録をつけることで草が生え、「今日も頑張った」と思える。
2. なぜ「思い出しながら書く」ことが重要なのか → インプットだけでは自分が認知できる範囲でしか理解できず、アウトプットすることで初めて他の人が認知できる形になる。インプットした知識を活かすには、アウトプットへのプロセスが必須である。
3. なぜアウトプットする機会や「頑張った」という実感が必要なのか → 学習は誰かと争うものではなく自分との戦いであり、継続しなければ見えてこないことがある。インプットした内容を思い出し取り出すことが真の理解には必要だが、アウトプットはインプットより負荷が高くしんどさを伴う。だからこそ、記録という行為には、続けるためのモチベーションを高める仕組みが必要である。

**本当に解決したい課題**: インプットした知識は、思い出して取り出す(アウトプットする)プロセスを経ないと本当の理解にならない。しかしアウトプットは負荷が高くしんどさを伴うため、続けるには外側からのモチベーション(見える形での積み重ね)が必要である。

## 4. 想定ユーザーについて

**4-1. 想定しているユーザー**

- **年齢設定**: 30代(ユーザーと同年代)。理由: 30代になると学習から10年以上遠ざかっており、学習方法から見直しが必要な段階にある。アウトプットより負荷の軽いインプットに寄りがちな年代だから。
- **生活・状況設定**: 仕事をしながら家庭があり、仕事・家事・育児に追われ、1日の学習時間が短い。アウトプットにかける時間が惜しくインプットに寄っている。いきなりアプリ開発のような大きなアウトプットを求めると挫折しやすいため、記録という小さなアウトプットを積み上げる場を作りたい。
- **環境設定**: 複数のAIを使い分けている人はそれほど多くないため、AIを使って学習していて学習記録もしているが、AIに要約してもらった内容を見るだけ、あるいはそれをコピペして記録しているだけの人を対象とする。

**4-2. 自分とユーザーの距離**

自分自身。プログラミングスクールの日報を毎日書いているが、AIを使った学習とそうでない学習が同じ1つの記録に混ざり、AIでの学習内容の記載密度が薄くなりがちで、1日に1つしか書けない。GitHubにリポジトリを作りコミットすれば草は生えるが手順が面倒で、Mattermostは草も生えずAI名などのテンプレート入力が面倒。

**4-3. 実際に使われる可能性について**

- 最初に使ってくれそうな人: AIを使って意欲的にプログラミング学習に取り組んでいる人。
- 使う場面: AIを使った学習がひと段落した時、1日の終わり。
- 既存の代替手段: プログラミングスクールの日報(密度が薄い)、GitHubコミット(手順が面倒)、Mattermost(草が生えない、テンプレ入力が面倒)。
- 置き換えてまで使う理由: log_aiはAIという技術が好きな人がAIについてだけの記録を残せる場所であり、その好きな技術で継続力を示すことができる。ターミナル操作は不要で、非エンジニアでAIが好きな人でも継続力を証明できる場になる。

**4-4. 導入・継続の流れ**

- きっかけ: AIに要約してもらっただけで何となく学習内容を把握して1日を終えたが、頭の中は整理できておらず、次の日には忘れている、という「頭の中がすっきりしない」感覚。
- 最初の一歩の障壁: アカウント登録。
- 続ける理由: 草を生やす達成感と、AIという技術が好きな人のAIについての記録を貯めていく仕組み。

**5-1. 似たサービスの調査**

| Habitify / Goal Streak | 習慣づけ・GitHub風の草で可視化する点は共通だが、目標達成を前提とした多機能なアプリで、目標設定や予定入力などの下準備が必要 |
| MydayAI(https://myday-ai.com) | 個人開発の日記型生活行動記録サービス。時間の使い方を記録しグラフ可視化・AI分析ができるが、AI活用に特化はしておらず、記録項目もタイムライン形式で入力に手間がかかる |
| AI Habit Tracker / PromptScore | ChatGPT等の利用を自動計測しストリークを表示するブラウザ拡張。AIによる提案や自動計測が主軸で、手動での意味づけ記録を目的としておらず競合ではない |

**5-2. それでも自分が作りたい理由**

競合アプリは目標を設定し、その達成のための予定入力や時間配分などの下準備が多い。それは多機能であるがゆえに生じる。log_aiはAIに特化して記録を作成し、投稿すると継続の証である草が生える、というシンプルな仕組みで、記録すること自体が目標達成になる。AIという技術が好きな人の「好き」が集まり、努力の結晶が見える場所でありたく、多機能である必要はない。

**5-3. 差別化を「体験価値」で表現する**

> このサービスは、AIという技術への「好き」を持て余している人が、日々の工夫を記録に残しながら、新しい使い方を探し続ける姿勢と、目に見える形の継続を育てていけるようになるサービス

## 7. このアプリで実現すること

**MVPで作る機能**
- アカウント登録・ログイン・パスワード再設定
- 活用記録の投稿・編集・削除(活用日・AI名・用途・本文)
- 直近1年間の草カレンダー(投稿数に応じた5段階の濃淡)
- キーワード・用途による検索(履歴の絞り込み)
- 履歴のページネーション(1ページ20件)

**本リリースで作る機能**
- SNS共有機能
- ファイル添付機能(「記録の省力化」のためではなく、「毎日記録しなければ」という義務感から生まれるしんどさへの"逃げ道"として位置づける)
- ChatGPTのような小さなAIマスコットキャラクター

※「記録の省力化」自体はMVP・本リリースともに実装しない方針。省力化するとアウトプットの機会を失うことになり、本サービスの価値の核と矛盾するため。

## 8. このアプリの懸念点とその対策

**懸念1: 記録の入力が面倒に感じられ、登録しても続かず離脱するリスク**
- 対策: 本文は文字数制限、用途はチェックボックス選択にすることで入力の自由度をあえて下げ、「何を入力したらいいか分からない」という迷いを省く。

**懸念2: 初期の少人数の中で、草が育つ実感が出るまでに時間がかかり離脱されるリスク**
- 対策: 草全体が育つには時間がかかるが、記録数に応じてマスの色が濃くなる仕組みにより、1件記録するたびに色の変化が即時反映され、成果が目で見て分かりやすいため、短いスパンでのフィードバックによって離脱リスクを抑えている。

**懸念3: 「多機能じゃないこと」自体が「物足りない」と感じられ使われなくなるリスク**
- 対策: 機能が少ないからこそ、サービスの核・目的を端的に伝えられる。刺激は少なく飽きられる可能性もあるが、その分習慣化しやすく、草を生やすこと自体も習慣化の後押しになっている。

## 9. 今後の展開・発展の方向性

- ユーザーはなぜ使い続けるか: AIという技術が好きであり、それ専用の記録サービスがあることで自分の「好き」を貯めていけるから。
- 続けることで何が変わるか: 好きをより追求しようという意欲につながる。
- データが溜まると何ができるか: AIという技術への追求、継続の証になる。
- 他の人と関わる余地はあるか: サービス内ではなく、X等に草が生えている様子や記録をスクリーンショットで投稿することで、他サービス上で関わる余地がある。
- 運用・仕組みで価値を出せないか: マスコットキャラクターの導入により継続の後押しや、離脱した人の出戻りを促したい。毎日記録するかはユーザー次第であり、義務感がしんどさにつながらないよう、ファイル添付という「逃げ道」の余地を用意することで、使い続けてもらいやすくする。

今考えている発展案: SNS共有機能・ファイル添付機能・AIマスコットキャラクター(7章参照)

## 10. 技術スタック

**10-1. 使用予定の技術**

- フレームワーク: Ruby on Rails 8系
- データベース: PostgreSQL(Neonでホスティング)
- デプロイ先: Render(Dockerfileを使用)
- 主なライブラリ: Turbo/Stimulus(Hotwire)、Bootstrap、kaminari、bcrypt

**10-2. 技術選定の比較検討**

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby on Rails 8系 | 採用 | スクールのカリキュラムは7系だったが、あえて最新の8系に触れる機会にしたい |
| PostgreSQL(Neon) | 採用 | サービスとして公開する以上、Renderの無料PostgreSQL(90日失効)に縛られず本番相当のDBを使いたい |
| SQLite | 不採用 | ミニアプリでの検証段階では採用してよいが、実サービスとしては同時書き込みやスケールの面で不向き |
| `has_secure_password`(自前実装) | 採用 | `devise`だと内部処理がブラックボックスになり、認証の仕組みを再学習する機会が失われるため |
| `devise` | 不採用 | 上記の理由により見送り |
| Dockerfile + Renderの標準デプロイ | 採用 | Kamalの検証ができるまでの、確実性の高い代替手段として |
| Kamalでのデプロイ | 不採用 | ミニアプリでの検証を経ておらず、いきなり本サービスに導入するにはリスクが高い |
| Minitest | 採用 | フレームワーク(RSpecのDSL)に頼らず、テストの書き方そのものを身につけたい |
| RSpec | 不採用 | 上記の理由により見送り |
| Bootstrap | 採用 | フレームワークの恩恵を受けつつ、草カレンダーなど独自部分でCSSを自力で書く力も並行してつけたい |
| Next.js(React)/Django(Python)/Node.js(Express) | 不採用 | 学習コストが高く、サービスとして完成させるための開発期間内に収まらない |

**今回チャレンジしたい点**: 草カレンダーの表現、Minitestでのテストコード記述

**不安な点**: 草カレンダーをしっかり表現できるか。頭の中でイメージはできているが、手を動かして経験値を貯めなければ応用力も手に入らないため、まず簡易的な草カレンダーをミニアプリとして先に開発する。

**10-3. キャッチアップ不足の懸念**

草カレンダーのCSS Grid実装、Minitestでのテスト記述はいずれも初挑戦に近い。完成イメージは頭の中にあるが、実装の見積もりの精度は手を動かしてみないと定まらない部分がある。そのため、本サービスにいきなり組み込むのではなく、まず簡易的な草カレンダーをミニアプリとして開発し、そこで得た経験値を本サービスの実装に活かす、という段階的な進め方を取る。
